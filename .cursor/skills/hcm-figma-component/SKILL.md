# Компонент Q.HCM в Figma

Ты собираешь компонент как опытный продуктовый дизайнер дизайн-систем, который понимает разработку. Результат — три вещи на странице компонента в файле DS-Q.HCM:

1. **Набор вариантов** (component set): все типы × наполнение × состояния, у каждого варианта понятное имя, все цвета, размеры, радиусы и отступы привязаны к переменным Q.HCM Tokens.
2. **Панель вариантов** слева: матрица всех вариантов с подписями строк и столбцов и плитки свойств экземпляра.
3. **Документ «<Компонент> · Правила использования»** справа: машиночитаемая спецификация для ИИ-агента, сверстанная как документ для человека. Структура и верстка — строго по `rules-layout.md`.

Перед первым вызовом `use_figma` прочитай скилл `figma-use`. Для экранов из компонентов — `minimalism-hcm-ds`. Верстка документа правил — `rules-layout.md`. Готовый стартовый промт для запуска задачи — `prompt.md`.

## Откуда брать решения

Решение по компоненту принимается не по вкусу, а по источникам. Проверяй в таком порядке:

1. **Прототип Q.HCM** — как элемент реально работает у пользователя: где стоит, какие размеры, какие состояния есть в CSS, какие классы и компоненты Angular его рисуют. Найди все варианты элемента в коде (grep по классам и компонентам), сведи их в один компонент.
2. **Правила продукта** (`AGENTS.md`) и **скилл ДС** (`minimalism-hcm-ds`) — обязательные договоренности: формы-страницы без «Отменить», сортировка только иконкой ⇅, счетчики в табах, кнопки объекта и т. п.
3. **Основы ДС в Q.HCM Tokens** — правила цвета, типографики, отступов, теней. Компонент не может им противоречить.
4. **Базовая библиотека** (обычно PrimeNG, на ней строился прототип) — полный перечень состояний, свойств и частей компонента, чтобы ничего не забыть.
5. **Лучшие практики дизайн-систем** — Material 3, Atlassian, Primer, Carbon, Meta Astryx: доступность (WCAG 2.1 AA), именование свойств, структура документации.

Если источники спорят: доступность → смысл и поведение у пользователя → правила продукта → как в прототипе → внешний вид. Каждое расхождение с прототипом (другой отступ, добавленное состояние, кольцо фокуса) не прячь — вынеси в итоговый ответ пользователю как решение, которое она подтверждает.

## Продуктовое мышление

До Figma ответь себе письменно (в рассуждении, не в документе):

- **Какую задачу пользователя решает компонент** и где он стоит на экранах Q.HCM: строка фильтров, форма-страница, сайдбар, модальное окно, таблица, карточка виджета.
- **Какие типы реально нужны.** Тип — это разное назначение или место, а не разный цвет. Лишние типы не заводи; похожие элементы с другим поведением — отдельные компоненты (Input ≠ Select ≠ Date ≠ Textarea).
- **Как выбрать тип** — упорядоченный список вопросов, первое подходящее правило решает.
- **Какие состояния видит пользователь** и когда каждое возникает: Default, Hover, Focus, Pressed / Active, Selected, Invalid, Disabled, Loading, Read-only — только те, что у компонента реально бывают.
- **Что может пойти не так**: длинный текст, пустое значение, ошибка, нет прав, загрузка, темная тема, узкий контейнер.
- **Что нельзя делать** с компонентом и почему — из реальных ошибок на макетах (плейсхолдер вместо подписи, разная высота в одной строке, состояние только цветом).
- **Какие тексты** внутри компонента: только нейтральные английские заглушки. Подпись значения — `Title`, вторая строка — `Subtitle`, человек — `Name` и `Position`. Длинный текст — повтор `Title`, чтобы было видно многоточие. Никаких ФИО, должностей, названий подразделений и других данных продукта внутри компонента.

Эти ответы и становятся содержанием разделов документа.

## Порядок работы

1. **Исследование.** Прочитай эталон Input в Figma, код прототипа, правила продукта, основы токенов, страницу базовой библиотеки. Составь таблицу: размер, отступы, радиус, рамка, шрифты, цвета каждого состояния — значение в прототипе и токен Q.HCM Tokens.
2. **Токены.** Найди переменные и стили только в Q.HCM Tokens (`search_design_system`, затем импорт по ключу `importVariableByKeyAsync` / `importStyleByKeyAsync`). Названия бери из библиотеки, не по памяти. Нет нужного токена — возьми ближайший по роли и сообщи пользователю; новый цвет или значение не придумывай. Переменную из Q.Palette Minimalism не импортируй, даже если она уже стоит на старом компоненте.
3. **Набор вариантов** — по разделу «Сборка компонента» ниже. Проверь скриншотом.
4. **Панель вариантов** — матрица и свойства. Проверь скриншотом.
5. **Правила** — по `rules-layout.md`, в два-три вызова (шапка → состояния, тексты → примеры). Проверь скриншотом каждый раздел.
6. **Самопроверка** — чек-лист в конце этого файла.
7. **Ответ пользователю** — итог первым предложением, затем таблица «прототип / компонент» и решения, которые нужно подтвердить. Код не трогать без команды.

## Сборка компонента

**Свойства.** Варианты — только то, что меняет устройство компонента:
- `Type` / `Label` / `Size` — тип или вид (значения с заглавной, по-английски: `None`, `Top`, `Infield`; `M`, `L`);
- `Content` — наполнение, если пустой и заполненный вид различаются (`Empty`, `Filled`);
- `State` — состояния: `Default`, `Hover`, `Focus`, `Pressed`, `Selected`, `Invalid`, `Disabled`, `Loading`.

Тексты — свойства `TEXT` (`Label text`, `Placeholder`, `Value`, `Hint text`). Части, которые включают и выключают, — `BOOLEAN` (`Icon`, `Clear`, `Required`, `Hint`). Иконки-замены — `INSTANCE_SWAP`. Не плоди варианты там, где хватает boolean или текста.

**Имена.** Вариант называется `Свойство=Значение, …` (Figma делает это сам). Слои — по смыслу: `Field`, `Label`, `Value`, `Placeholder`, `Icon`, `Hint`, `Focus ring`. Никаких `Frame 12`, `Rectangle`.

**Полнота.** Матрица = все типы × все наполнения × все состояния, без пропусков. Если сочетание невозможно, исключи его осознанно и напиши об этом в правилах.

**Тексты внутри компонента — нейтральные заглушки на английском.** Так же устроены Material и Human Interface: компонент не знает про банк. Значения по умолчанию и текст в каждом варианте:

| Что на макете | Заглушка |
|---|---|
| Название значения, пункта, поля | `Title` |
| Вторая строка | `Subtitle` |
| Человек | `Name` |
| Должность, роль | `Position` |
| Длинное значение, чтобы проверить многоточие | `Title` несколько раз подряд |

Фамилии, должности, подразделения, даты и суммы внутрь компонента не писать. В документе правил язык русский, но экземпляры компонента и там показывают эти же заглушки. Продуктовый пример живет в подписи рядом («фильтр подразделения»), не в тексте компонента. У одного текстового свойства одно значение по умолчанию: если заглушки разные (`Title` и `Name`), это два свойства.

**Готовые части — экземплярами.** Перед тем как нарисовать аватар, чекбокс, радио или другой уже существующий элемент, найди его в DS-Q.HCM и поставь экземпляр. Avatar — со страницы Avatar. Не копируй его вектором и не собирай второй.

**Иконки — только из Q.Icons.** Значок — экземпляр компонента этой библиотеки (свойство `INSTANCE_SWAP`, значение по умолчанию — нейтральный знак, например `Icons / plus`). Компонент Icon со страницы Icon — плитка объекта, ее в ряд высотой 36 не уменьшать. Иконки из Q.Palette Minimalism и Q.PALETTE web не брать. Цвет значка перекрашивай семантическим `color/icon/*` из Q.HCM Tokens, если заливка внутри экземпляра пришла из другой библиотеки.

**Верстка варианта.**
- Auto layout везде. Ширина варианта фиксированная (по умолчанию 240), внутреннее поле — Fill. Высота строки кратна 4. Однострочный пункт и контрол — **36** (`size/control-m`). Если стиль `UI/Body 2` (14/18) с отступами 8 дает 34, высоту все равно фиксируй 36 и выравнивай содержимое по центру. 34 не оставляй. Строка с подписью и строка с аватаром — тоже кратны 4 (52 и 48).
- Отступы, gap, радиус, толщина рамки — привязаны к переменным шкалы Q.HCM Tokens. Значения только кратные 4.
- Текст — только текстовыми стилями библиотеки (`UI/Body 2`, `UI/Description 1` …), длинный текст обрезается многоточием в одну строку (`textTruncation: 'ENDING'`, `maxLines: 1`).
- Цвета — только семантические переменные `color/*` коллекции `Color` библиотеки Q.HCM Tokens. Запрещены hex, примитивы (`primary/500`, `ink/*`) и любая переменная библиотеки Q.Palette Minimalism.
- Кольцо фокуса — отдельный слой `Focus ring` по размеру поля с внешней рамкой 3 px (`focus/width`) цвета `color/focus/control` (или `color/focus/ring` для кнопок), радиус = радиус поля + 3. Тень с переменной цвета для кольца не используй: из библиотеки она не отрисовывается.

**Цвета по ролям** (из правил Q.HCM Tokens):

| Часть | Токен |
|---|---|
| Фон контрола / недоступный | `color/background/surface` / `color/background/disabled` |
| Рамка / наведение и фокус / ошибка / недоступная | `color/border/default` / `color/border/brand` / `color/border/error` / `color/border/disabled` |
| Значение / подпись над полем / вспомогательный текст | `color/text/primary` / `color/text/secondary` / `color/text/muted` |
| Плейсхолдер / недоступный текст | `color/text/placeholder` / `color/text/disabled` |
| Текст и иконки контролов (селект, таб, кнопка-иконка) | `color/text/control` / `color/icon/control` |
| Активная подпись, ссылка, выбранное | `color/text/brand`, `color/background/brand`, `color/background/brand-subtle` |
| Ошибка: текст, звездочка обязательности | `color/text/error` |
| Иконка внутри поля | `color/icon/muted` |
| Кнопки | `color/action/<вариант>/background`, `-hover`, `-pressed`, `-disabled`, `/foreground` |
| Бейджи | `color/badge/<тип>/background` + `/foreground` |
| Статусы вне бейджа | `color/background/<статус>-subtle`, `color/text/<статус>`, `color/icon/<статус>`, `color/border/<статус>` |
| Плашка-подсказка, KPI | `color/background/muted` |

Фон и текст всегда из одной группы. Состояние никогда не передается только цветом.

## Как писать правила

- **Это готовая спецификация.** Ни истории правок, ни пересказа переписки, ни «раньше было», «теперь», «исправлено», «серой кнопки нет». Агент читает документ без контекста диалога.
- **Каждое правило — проверяемое действие.** «Ошибку показывают после ухода из поля или при отправке формы» вместо «ошибка должна быть понятной».
- **Называй точные имена**: свойства Figma (`Label=Infield`), токены (`color/border/brand`), классы и компоненты кода (`app-field`, `.fin`), размеры в px.
- **Объясняй почему** одной фразой после двоеточия, если причина неочевидна: «Invalid всегда с текстом: один цвет не говорит, что исправить».
- **Экземпляры в документе показывают заглушки** `Title`, `Subtitle`, `Name`, `Position`. Подпись под примером может назвать экран Q.HCM, но не подменяет текст внутри компонента.
- **Язык документа.** Русский, буква «е» вместо «ё», кавычки «ёлочки», тире «—». Короткие предложения. Термины Figma, токены и заглушки — латиницей как есть.

## Технические правила Figma

- `use_figma` вызывай строго по одному, не параллельно. В начале каждого скрипта — `await figma.setCurrentPageAsync(page)`.
- Скрипт с ошибкой откатывается целиком — после ошибки исправь и повтори весь скрипт.
- «fetch failed» и «Not connected» — временные; повтори один раз, при повторе остановись и сообщи пользователю.
- Перед изменением текста — `figma.loadFontAsync(node.fontName)`.
- `node.fills` возвращает новую копию при каждом чтении: меняй копию массива по индексу и присваивай обратно, не сравнивай краски через `===`.
- Привязка цвета: `figma.variables.setBoundVariableForPaint(paint, 'color', variable)`; отступы и радиусы — `node.setBoundVariable('paddingLeft', v)` и т. п.
- Переменные библиотеки — через импорт по ключу; новые токены появятся в DS-Q.HCM только после публикации библиотеки и принятия обновления.
- Большие скрипты дели на части; результат каждого шага проверяй скриншотом `get_screenshot`.
